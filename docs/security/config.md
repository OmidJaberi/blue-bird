# Security Configuration

## Overview

The security module's behavior is governed by an explicit, validated
policy object rather than hardcoded constants scattered through the
password and session code.

---

# Public Header

```c
#include <blue-bird/security/config.h>
```

---

# What's Configurable

```txt
bb_security_config_t
├── password_pbkdf2_iterations   PBKDF2-HMAC-SHA256 cost for bb_password_hash()
├── password_max_length          rejected above this, by hash() and verify()
├── session_lifetime_seconds     default ttl used by bb_auth_login()
└── session_id_length            hex characters generated by bb_session_create()
```

Everything else about the password/session implementation (the hash
algorithm itself, salt size, record format) is not policy - it's an
implementation detail, and stays fixed.

---

# Defaults and Validation

```txt
bb_security_config_default()
    ↓
built-in secure defaults
    ↓
bb_security_config_validate()
    ↓
OK, or BB_ERR_INVALID_SECURITY_CONFIG
```

Every field has an enforced range - a too-low iteration count, an
oversized password limit, a multi-year session lifetime, or a
too-short session ID are all rejected rather than silently accepted.
`bb_security_config_default()` always returns a config that passes
`bb_security_config_validate()`.

---

# Setting the Active Configuration

```c
bb_security_config_t config;
bb_security_config_default(&config);

config.session_lifetime_seconds = 1800; /* 30 minutes */

bb_error_t err = bb_security_config_set(&config);
```

`bb_security_config_set()` validates before installing - on failure,
whatever was active before (or the default, if this is the first call)
is left in place. Do this once, during application startup, before
anything starts handling requests: like the rest of the session
subsystem, the active configuration is process-wide state with no
locking, on the assumption of Blue-Bird's single-threaded event-loop
runtime.

`bb_password_verify()` is the one exception to "active config governs
behavior": it reads the iteration count back out of the record it's
checking, not from the current config, so changing
`password_pbkdf2_iterations` later never invalidates already-stored
password hashes.

# Loading From a Config File

```c
bb_json_t *json = bb_json_create(BB_JSON_OBJECT);
bb_config_load_env(json, ".env");

bb_security_config_t config;
bb_error_t err = bb_security_config_from_json(json, &config);

if (err.code == BB_OK)
{
    bb_security_config_set(&config);
}
```

Recognized keys (all optional - only mention what you want to change):

```txt
security_password_iterations
security_password_max_length
security_session_lifetime_seconds
security_session_id_length
```

`bb_security_config_from_json()` starts from the defaults and only
overrides the keys actually present, then validates the combined
result. It never calls `bb_security_config_set()` for you, the same
way `bb_tls_config_from_json()` never starts a server for you.
